# 编程交互学习模式调研

> 调研日期：2026-10-20
> 用途：指导 Go + Wails + React 教程的整体重构
> 边界：只借鉴教学思路与交互机制，不复制任何产品的文案、视觉或实现。

## 结论先行

主流交互编程产品的共同点不是“加更多按钮”，而是缩短从理解到行动再到反馈的距离：一次只教一个变化，学习者在同一视图中预测、改代码、运行、看结果，然后带着这一小步的经验进入下一步。

对本项目最关键的改造方向是：

1. 从“一章多块内容”改为“一屏一个学习任务”。
2. 每个任务都固定遵循`看现象 -> 猜结果 -> 改一处 -> 运行 -> 解释 -> 再改一次`。
3. 普通 Go 代码是主体；Wails 只负责把 Go 方法接到桌面界面，React 只负责输入与展示。
4. 运行、提示、切换小步都不得改变页面的纵向位置；只有学习者明确切换章节时才回到新章起点。
5. 反馈先回答“哪里不符合”，再给当前知识点提示，最后才展示部分写法；不在第一次失败后直接给完整答案。

## 不应直接照搬的部分

- 不采用“全锁定”路线。完全锁定会阻碍有基础的学习者定点复习；本项目应像 Exercism 一样分成默认引导模式和可随时进入的自由浏览模式。
- 不用积分、连续天数替代掌握证据。本项目的进度应来自“预测过、修改过、运行过、通过测试”。
- 不复制视频形式。Scrimba 值得借鉴的是“讲解现场与可编辑代码合一”，而不是录屏本身。
- 不让 AI 直接代写完整答案。AI 只应根据本次失败给一个可执行的下一步。

## 本项目的新教学单元

每个单元只允许一个新的 Go 知识点，最长预期完成时间为 5–10 分钟。

| 阶段 | 学习者行为 | 界面中可见内容 | 完成证据 |
| --- | --- | --- | --- |
| 1. 看现象 | 运行一份不超过 20 行的可完整执行代码 | 一句目标、完整代码、单一运行按钮 | 运行结果已显示 |
| 2. 猜结果 | 运行前选择或输入预测 | 最多 3 个选项，不引入未教过术语 | 预测已锁定 |
| 3. 改一处 | 只改 1–3 行，观察差异 | 编辑边界高亮，其他代码可阅读但不要求修改 | 代码已变更 |
| 4. 运行与反馈 | 执行或跑测试 | 结果紧邻编辑器，反馈指向当前一步 | 断言或测试通过 |
| 5. 说出原因 | 用一句话回答“为什么” | 先显示自己的解释，再展示标准解释 | 已完成自我解释 |
| 6. 迁移 | 在新输入上再做一次 | 相同语法、不同业务值 | 第二个测试通过 |

### 一个单元不得同时引入的内容

- 教 `struct` 时，可以展示 React 收到对象，但不在同一单元解释 hooks、组件通信或 Wails 生命周期。
- 教方法接收者时，只让按钮调用一个 Go 方法，不同时引入接口和依赖替换。
- 教 `error` 时，用同一输入分别触发成功和失败，不混入并发。
- 教 `context` 时，先在纯 Go 中取消一个循环，然后才用 Wails 把取消按钮接上去。

## 知识连续性规则

### 可见的先修关系

每个单元顶部只显示三项：

- `你已会`：本节真正使用的 1–2 个旧知识。
- `这一节只学`：唯一新知识。
- `学完可以`：一个可执行的行为。

如果某节无法用这三项说清，就应继续拆分，而不是增加更长的解释。

### Go -> Wails -> React 的固定顺序

```text
纯 Go 函数可运行
  -> 为自定义类型添加方法
  -> 方法通过 Go 测试
  -> Wails 绑定这个对象
  -> React 调用生成的绑定
  -> 界面展示同一个 Go 结果
```

其中只有第 1–3 步用于判定 Go 语法是否掌握。Wails 和 React 的任务是让结果可见、可点、可反复尝试，不是增加第二条技术主线。

## 练习递进梯度

同一个 Go 知识点应按以下顺序至少出现三次：

1. **读与预测**：不写代码，先判断输出或错误。
2. **局部修改**：在已运行的代码中改 1–3 行。
3. **填写核心**：只补齐当前知识点对应的函数体。
4. **诊断故障**：根据编译错误或失败测试找出一处原因。
5. **独立实现**：只给函数签名、行为要求和测试。
6. **可见迁移**：把已通过测试的 Go 方法连到 Wails + React 小界面。

不得将“跑通已写好的大段代码”计为独立练习。

## 反馈机制

### 四层反馈

1. **结果层**：通过或未通过，并显示实际值与期望值。
2. **位置层**：指向最小的相关行、函数或概念，不仅给原始编译日志。
3. **概念层**：解释当前规则，例如“只有导出字段会被 `encoding/json` 编码”。
4. **方向层**：给下一个可尝试动作，但不直接替换学习者的整份代码。

### 逐级提示

- 提示 1：回忆规则。
- 提示 2：指出检查位置。
- 提示 3：给与当前数据不同的微型例子。
- 完整解法：学习者主动展开，且展开后该单元不标记为“独立通过”。

Exercism 的官方辅导指南建议每次只给最重要的 1–3 条反馈，并强调通过提示帮助学习者自己得出解法，而不是直接给答案。[官方反馈指南](https://exercism.org/docs/mentoring/how-to-give-great-feedback)

## 导航、滚动与焦点规则

用户反馈中“点了又跳到上面”属于交互状态错误，不是动画或样式问题。应落实为以下可测试规则。

### 状态层级

```text
课程
  章 chapter
    知识串 concept thread
      学习单元 unit
        小步 step
```

- 仅“切换 chapter”可将新章顶部对齐到视口。
- 切换 unit 时，将单元标题对齐到粘性顶栏下方，不跳到文档顶部。
- 切换 step、运行代码、打开提示、查看解释时，保持当前 `scrollY`。
- 代码运行后将焦点移到结果标题，但不滚动；屏幕阅读器通过 `aria-live` 获知结果。
- 如果结果完全不在视口内，只滚动结果容器到最近的可见边缘，不使用 `scrollIntoView({ block: "start" })`。
- 关闭对话框、提示层或目录后，焦点必须回到触发它的控件。
- 刷新或返回章节时，恢复 `chapterId + unitId + stepId + editorDraft + result + scrollAnchor`，不只恢复 hash。

### 导航形式

- 左侧目录所有章节和单元都必须是真正的链接或按钮，具有明确焦点样式和当前项 `aria-current`。
- 页面主区始终保留“上一小步 / 下一小步”，并显示如 `3 / 7`的局部进度。A Tour of Go 将前后页及键盘翻页作为主要导航，是这一模式的直接证据。[Tour 导航](https://go.dev/tour/)
- 自由浏览不要破坏引导进度；引导模式中的“继续学习”永远回到最后一个未完成小步。

## 页面信息架构建议

### 桌面宽屏

```text
左侧：可折叠路线（240–280px）
中间：当前小步说明（限宽，不独立长滚动）
右侧：编辑器 + 运行结果（保持稳定尺寸）
底部：上一步 / 运行 / 下一步（单一局部操作条）
```

可参考 Codecademy 官方描述的多区域语义结构，但不复制其视觉。[官方可访问性说明](https://www.codecademy.com/article/accessibility-on-the-platform)

### 窄屏

- 当前小步说明在上，编辑器和结果在下，不做三列硬缩放。
- 目录使用抽屉；关闭后回到原触发点。
- 运行后不自动跳到页顶或下一节。
- 代码区有最小高度和水平滚动边界，长行不撑宽页面。

## 内容重组的可执行规则

1. 先为现有内容建立先修图，任何节点有超过 2 个未教过的依赖时必须拆分。
2. 每章只保留一条主问题，不在标题层并列多个抽象目标。
3. 每 3–5 个微单元放一次复习，要求解释代码差异，而不只做选择题。
4. 每个概念至少在“局部修改”和“新输入迁移”中各出现一次。
5. 每一个 Wails + React 示例都要标出哪些行是 Go 语法、哪些行只是适配层，默认折叠适配层。
6. 完成章节的条件是末尾迁移题通过，不是滚动到页底或点击“我已阅读”。

## 优先级与验收标准

### P0：先消除学习中断

- 点击预测、运行、提示、复原、切换小步，`scrollY` 变化不超过 8px。
- 连续完成 10 个小步时，没有任何一次整页刷新或跳到顶部。
- 每个小步有且只有一个主要操作。
- 错误反馈在输出区内展示，且至少包含失败位置和下一个行动。

### P1：再重建知识连续性

- 每节只有一个新的 Go 知识点。
- 每节的先修知识都可点回对应微单元，并在返回时恢复原状态。
- 从纯 Go 到 Wails + React 的每次迁移只增加一层适配，不同时引入新 Go 语法。
- 每章末尾的独立题能被自动测试判定，不依赖主观勾选。

### P2：最后扩展自由实验

- 任何已通过的示例都能一键送入自由编辑区。
- 自由编辑不会覆盖引导模式的原始代码和进度。
- 学习者可重置当前小步，不必重置整章。
